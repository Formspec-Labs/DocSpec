## Findings first

There are **no BLOCKER or CONCERN findings**. The following are optional acceptance refinements, not missing architectural subsystems or additional prerequisites for the first fixed-schema fixture. Each attaches to work already assigned by the proposal.

### F1 — Make discovered dependency omissions an explicit reuse test

**Severity:** OPTIONAL. **Category:** conformance / acceptance precision. **Recommendation:** KEEP the reuse design; add a named case to its existing qualification matrix.

**Evidence.** The proposal correctly makes material dependency adequacy the basis for reuse ([R3 lines 15–19](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/03-schema-backfill.md:15)); R3-T01 already owns dependency/version rules ([R3:53](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/03-schema-backfill.md:53)). Core additionally requires a discovered omission to remain recoverable, cease authorizing affected reuse, and preserve the original record ([Core lines 229–237](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/core-model.md:229)). The current matrix names receipt, implementation, policy, and validator changes, but not discovery of an erroneous historical dependency declaration ([R7:59](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/07-operations-qualification.md:59)).

**Counterexample to test.** A classification result was recorded as depending only on text. The implementation later establishes that language was also material. A pending worker already resolved that result as reusable for a new language value. If completion lookup continues to rely on the old declaration, or the worker commits an unsupported adoption after learning the omission, the immutable old bytes do not make the new association correct. Equally, rewriting the old execution to pretend it declared language would falsify history.

**What already covers it.** R3 requires conservative treatment of uncertain adequacy; R1-T02 owns guarded commits and conflicting reuse; Core supplies the normative meaning. This is not evidence that the proposal permits the bad behavior.

**Smallest refinement.** Add one case under R3-T01/R3-T07 and R7-T04: record supplemental omission evidence without modifying historical provenance, then refuse affected reuse unless corrected historical evidence establishes correspondence. The concrete catalog representation belongs to those tasks; a new invalidation service is unnecessary.

**Falsifiable acceptance.** Pause reuse after lookup; record the omission; resume. No new association may justify reuse by ignoring the omission. The old result and its original declaration remain inspectable. Unaffected work remains eligible. Adequate supplemental evidence may qualify adoption, while unknown historical inputs remain unknown. Passing this case closes the refinement.

### F2 — Use an inconsistent related-input vector as the promotion litmus test

**Severity:** OPTIONAL. **Category:** named-seam / acceptance precision. **Recommendation:** KEEP captured-version promotion; instantiate its already-required relationship rule in a fixture.

**Evidence.** Per-input nonregression alone appears in the overview ([README:78](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/README.md:78)), but the detailed plan also requires the catalog transaction to validate input relationships ([R5:29](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/05-dependent-refresh.md:29)). R5-T01 expressly owns input consistency and simultaneous input examples ([R5:45](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/05-dependent-refresh.md:45)); publication checks application-defined relationships ([R2:25](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/02-incremental-publication.md:25)).

**Counterexample to test.** Let a producer declare Comments C2 and Dockets D2 as one related publication generation. Refresh captures C2 and D1. Both components equal or follow the prior consumer coverage C1/D1, and a full join faithfully reproduces C2/D1, but that vector violates the producer's declared relationship. Neither componentwise order nor agreement with a full reconstruction of the wrong vector proves admissibility.

**What already covers it.** The linked plan requires relationship validation, exact coverage, and refusal/reconciliation. Actual application relationships are explicitly left for R2-T01 and R5-T01; they are legitimate product/schema inputs, not a reason to invent a global transaction across independent publishers.

**Smallest refinement.** Put this example beside the shared promotion inputs, with one admissible mixed vector for genuinely independent sources and one inadmissible mixed vector for explicitly coupled sources. No distributed transaction or global watermark is required.

**Falsifiable acceptance.** A candidate over C2/D1 must be refused when the declared generation rule requires C2/D2, even though coverage never regresses and the candidate matches full processing of C2/D1. C2/D2 must pass. With independent-source semantics explicitly selected, the mixed vector may pass and must report its exact pins. Passing demonstrates that “consistent” has application meaning beyond monotone counters.

### F3 — Make the cross-system recovery tests preserve the original attempt identity

**Severity:** OPTIONAL. **Category:** recovery / acceptance precision. **Recommendation:** KEEP durable intents and fenced external effects; run the delayed-attempt sequence explicitly.

**Evidence.** The architecture does not pretend the catalog and external pointer form one transaction. It requires pre-effect intent, exact reconciliation, and storage-boundary fencing ([README:90](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/README.md:90); [R2:27](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/02-incremental-publication.md:27)). R2-T04 already calls for authority-handoff races and prohibits an old attempt from adopting a replacement epoch ([R2:38](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/02-incremental-publication.md:38)).

**Counterexample to test.** Publisher A records intent under epoch e1 and pauses before its external write. Authority moves to B/e2, but B has not yet advanced the pointer. A resumes with the still-matching expected pointer. A plain compare-and-swap succeeds unless the storage boundary also fences its authority. A second hazard is retry code silently obtaining e2 and relabeling A's old attempt.

**What already covers it.** The exact dangerous behavior is already forbidden in R2:27 and T04. A catalog lease check is explicitly insufficient. This finding adds no missing requirement and is not a reason to reject the design; it identifies the decisive provider qualification sequence.

**Smallest refinement.** Retain this interleaving as a named R2-T04/R7-T05 test, including the unchanged external pointer and attempted epoch substitution. Keep the old attempt identity visible in the result.

**Falsifiable acceptance.** After e1 is fenced, A cannot advance the pointer even while its expected pointer token still matches, and cannot acquire e2 for that same attempt. Crash after B's successful public write but before local reconciliation; recovery must identify that exact release and resume readback without another public write. A real-provider failure of this test rejects that provider/deployment mechanism, not the catalog-plus-immutable-data architecture.

## Artifact summary and decision frame

The proposal is **product architecture supported by operational and proof work**. Its users are dataset producers, operators recovering expensive jobs, and consumers needing reproducible releases. Inputs are pinned source values and evidence. The engine resolves qualified results, processes affected batches, retains independently useful phases, and selects a complete output. Outputs are exact dataset versions and independently readable releases. Independent reconstruction, failure injection, and whole-lifecycle measurements check the result ([README lines 49–107](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/README.md:49)).

## User value, debt, and smaller shapes

The strongest user-value claim is recovery: a completed receipt transfer or matching phase remains useful after later validation or report failure. That directly addresses the research cases and is executable as first-delivery acceptance ([RESEARCH lines 26–39](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/RESEARCH.md:26)). Independently versioned field groups add a second plausible benefit: paying for an enrichment's changed inputs and outputs without rewriting unrelated columns. The proposal correctly includes the cost of joining or materializing those groups before selecting their layout ([R3:35](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/03-schema-backfill.md:35)).

Conceptual debt is deliberate: separate occurrence/value identities, exact input vectors, dependency adequacy, retained phases, authority epochs, and retention roots. These distinctions prevent different concrete failures; collapsing them into “latest table version” would lose meaning. The design limits additional debt by reusing maintained transactions and query/storage engines, refusing a second cursor/job journal, and deferring a general incremental SQL compiler ([R1:15](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/01-durable-storage.md:15), [R5 lines 13–17](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/05-dependent-refresh.md:13)).

Applying the requested priority frame, the high importance and direct operator value of phase recovery justify its proof work. The rewrite language and storage candidate have weaker evidence: their future debt is justified only if the bounded complete-path probes pay for it. A full rebuild with recoverable phases remains a smaller valid execution strategy for small datasets or global transformations. A wide table remains a valid physical baseline when groups change together. Neither alternative removes the need for honest evidence, retained results, guarded selection, or safe cleanup.

**Six-month falsifier:** on equivalent inputs and guarantees, unchanged/resumed jobs still repeat qualified expensive work, or fixed-size changes pay growing full-dataset costs without a documented necessary stage, while field-group joins and catalog complexity add cost. That would defeat the intended benefit and require reshaping the measured dominant stage ([README:149](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/README.md:149)). Merely using Rust or writing fewer files would not rebut it.

## Counterfactuals and component checks

- **Kill criterion:** reject a selected component/deployment if it cannot keep acknowledged outputs available after the promised failure, enforce selection/removal exclusion, or prevent a fenced publisher from writing. Reject the incremental path if it cannot match independent reconstruction for its supported rules. Those are existing gates, not newly invented production targets ([R7 lines 55–77](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/07-operations-qualification.md:55)).
- **Opposite decision:** a single mutable table and rerun-everything workflow reduces metadata vocabulary, but loses independently recoverable phases and cannot by itself preserve exact old evidence or coordinate public releases. A full-rebuild engine over the proposed immutable/result model is a sound fallback and useful baseline.
- **Removal probe:** remove the catalog and the first broken consumer is a reader needing one consistent data/schema/evidence selection after a crash between separate table commits. Remove R4's optional changes instead and correctness survives through full comparison ([R4 lines 23–27](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/04-change-tracking.md:23)). This distinction is well drawn.
- **Sibling subsumption:** the native format can subsume fragment management, backfill files, indexing, and table-level snapshots. It does not subsume application evidence meaning, complete cross-group selection, phase status, disclosure, or recovery promises. Avoid writing equivalent native storage machinery; the proposal already instructs this ([README:47](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/README.md:47)).
- **Future critic:** the main risk is that precise semantic obligations become too expensive to validate across every fragment and historical root. The prescribed fixed-change/growing-history experiment, counters, and cold/resumed arms are the right discriminator; no complexity bound or speedup should be inferred now ([R7 lines 81–87](/Users/mikewolfd/Work/spicy-stack/DocSpec/docs/plans/native-dataset-lifecycle-2026-10-07/07-operations-qualification.md:81)).

Primary documentation checked during this review supports the narrow component facts: Lance describes immutable version manifests and fragments with separate column files suitable for attaching backfilled columns. It also permits an external manifest store for commit coordination. This supports candidacy, not compatibility with all DocSpec guarantees. [Lance table format](https://lance.org/format/table/)

DataFusion describes itself as a Rust query engine using Arrow and documents `execute_stream` as producing record batches incrementally. That does not establish bounded memory for every join, aggregate, decoder, or writer. The proposal already requires spilling, cancellation, whole-process measurement, and complete-path probes.
